# Shule MS — Kenyan High School Management System

A school management system built for how Kenyan secondary schools actually
run today: **CBC (Grade 9–12) and 8‑4‑4 (Form 1–4) side by side**, since
most schools currently have both cohorts of learners at once.

---

## 1. How the domain model maps to how a Kenyan high school works

| Real-world concept | Model(s) |
|---|---|
| School (single school, e.g. "Kenya High"), mixed/boys/girls | `School` |
| Academic Year, Term 1/2/3 | `AcademicYear`, `Term` |
| CBC vs 8‑4‑4, Grade 9 vs Form 2, JSS vs SSS | `CurriculumType`, `GradeLevel` |
| Streams (Red, Blue, Green) per grade per year | `Stream`, `ClassRoom` |
| A student's yearly class + history preserved across promotion | `Enrollment` (**one row per student per year** — promoting a student creates a *new* `Enrollment`, the old one and everything linked to it is untouched) |
| Admission number ≠ login/user id | `StudentProfile.admission_no` is separate from `User.id` (a UUID) and `User.username` |
| Compulsory vs optional subjects, min/max subject count | `GradeSubject`, `SubjectSelectionRule`, `StudentSubjectSelection` |
| Subjects with two papers (Maths PP1/PP2, English PP1/PP2/PP3) — CBC *and* 8‑4‑4 | `Subject.has_papers` + `SubjectPaper` |
| A teacher teaching the same subject in two streams (Grade 9 Red English + Grade 9 Green English) | `TeacherSubjectAllocation` (unique per teacher+subject+classroom+year, so both rows can exist) |
| Opening / Midterm / End‑term exams | `ExamType` (configurable, with a `weight` and flags for whether it counts toward midterm/endterm ranking), `Exam` |
| Teachers entering marks from their own portal | `ExamResult`, scoped by RBAC + `TeacherSubjectAllocation` so a teacher can only key in marks for what they're allocated |
| Different grading scales per subject/curriculum (CBC "Exceeding Expectation" vs 8‑4‑4 "A–E") | `GradingScale` |
| Position/ranking at midterm and at end of term | `TermPositionRanking`, computed by `services.rank_classroom()` / `services.rank_grade()` |
| Minimum marks required to be promoted | `PromotionRule`, applied by `services.promote_student()` |
| Fee structure that differs by grade **and** by term | `FeeStructure` (unique per grade+term) → `Invoice` → `Payment` |
| Admin / Teacher / Student / Parent / Finance portals | `User.role` + DRF permission classes in `utils.py` |

## 2. Backend (Django + DRF) — single app, as requested

```
backend/
├── manage.py
├── requirements.txt
├── .env.example
├── config/                 # project-level settings & routing
│   ├── settings.py
│   ├── urls.py              # MAIN urls.py
│   ├── wsgi.py / asgi.py
└── school/                  # the one API app
    ├── models.py            # every model described above
    ├── serializers.py       # DRF serializers, incl. admit-student & bulk mark entry
    ├── services.py           # business logic: ranking, promotion, invoicing, admission numbers
    ├── utils.py              # RBAC permission classes + small helpers
    ├── views.py              # viewsets/APIViews — thin, call services.py
    ├── urls.py                # APP urls.py
    └── admin.py               # Django admin registrations
```

### Why the logic is split this way
- **`models.py`** — data shape only.
- **`services.py`** — the actual school-business rules (ranking formula,
  promotion eligibility, invoice generation). Kept out of views so it can be
  unit-tested and reused from Django admin actions / management commands / a
  future Celery task without touching HTTP code.
- **`utils.py`** — RBAC permission classes (`IsAdmin`, `IsTeacher`,
  `IsAdminOrTeacher`, `IsAllocatedTeacherForClassroom`, etc.) and small
  read helpers.
- **`views.py`** — parses the request, calls a service, returns a response.

### RBAC
`User.role` is one of `ADMIN`, `TEACHER`, `STUDENT`, `PARENT`, `FINANCE`.
Every viewset sets `permission_classes` accordingly, and list endpoints for
students/parents are further filtered in `get_queryset()` so a student can
only ever see their own records and a parent only their linked children's.

### Admission numbers
`StudentProfile.admission_no` is generated by
`services.generate_admission_no()` as `<intake year>/<sequence>` (e.g.
`2026/0007`) and is completely independent of `User.id` (a UUID primary
key) — changing/reissuing an admission number never touches login
credentials or foreign keys elsewhere in the system.

### Setup

```bash
cd backend
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
python manage.py makemigrations
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

API is served at `http://127.0.0.1:8000/api/v1/`. Auth:

```
POST /api/v1/auth/login/          { username, password } -> { access, refresh, user }
POST /api/v1/auth/refresh/        { refresh } -> { access }
GET  /api/v1/auth/me/
POST /api/v1/auth/change-password/
```

### A first-time setup sequence (typical school year rollout)

1. Create `School`, `AcademicYear` (`is_current=True`), 3 `Term`s.
2. Create `GradeLevel`s for both curricula (Grade 9–12 CBC, Form 1–4 8‑4‑4)
   and chain them with `next_grade` for promotion.
3. Create `Stream`s (Red/Blue/Green) and `ClassRoom`s (grade × stream × year).
4. Create `Subject`s, mark `has_papers` where relevant, add `SubjectPaper`
   rows (PP1/PP2), then `GradeSubject` (compulsory/optional per grade) and
   `SubjectSelectionRule` (min/max optional subjects).
5. Create `ExamType`s: Opening (counts toward nothing), Midterm (`counts_towards_midterm_rank=True`),
   Endterm (`counts_towards_endterm_rank=True`), each with a `weight`.
6. Create `GradingScale` rows per curriculum (and per subject if it differs).
7. Create `PromotionRule` per grade (minimum average % to move up).
8. Create `FeeStructure` + `FeeStructureItem`s per grade per term.
9. Admit students via `POST /api/v1/students/admit/` (auto-generates
   admission number + login + first `Enrollment`).
10. Allocate teachers via `TeacherSubjectAllocation` (admin), teachers then
    call `GET /api/v1/my-allocations/` from their own portal.

### Key endpoints beyond standard CRUD

```
POST /api/v1/students/admit/                      admit a new student
POST /api/v1/enrollments/{id}/subjects/            set a student's subjects for the year
POST /api/v1/exam-results/bulk_entry/              teacher submits a whole mark sheet at once
POST /api/v1/rank/                                 { term_id, classroom_id|grade_level_id, checkpoint }
POST /api/v1/enrollments/{id}/promote/             promote one student
POST /api/v1/enrollments/bulk_promote/             promote a whole classroom
POST /api/v1/invoices/generate/                    generate an invoice from the current fee structure
POST /api/v1/payments/                             record a payment against an invoice
GET  /api/v1/my-allocations/                       teacher: "what am I teaching this year?"
```

Each role has **its own `pages/<role>/` directory**, as requested — nothing
is shared between portals except the layout chrome (`Sidebar`, `Navbar`)
and the `services/api.js` client.

`Admin/Dashboard.jsx` and `Admin/Students.jsx` (list + admit-student form)
are fully wired to the API as a working reference; the rest of the pages
are scaffolded with the exact `api.js` calls to wire up next, so the shape
of the whole app is already in place.

## 4. Design decisions worth knowing about

- **History is never overwritten.** A student is never mutated onto a new
  class — a new `Enrollment` row is created and linked back via
  `promoted_from`. All marks (`ExamResult`), fee invoices (`Invoice`) and
  rankings (`TermPositionRanking`) hang off the `Enrollment` they happened
  in, so last year's Grade 9 record is exactly as it was, forever.
- **CBC and 8‑4‑4 run in the same tables**, distinguished by
  `curriculum_type` on `GradeLevel`, `Subject`, `StudentProfile` and
  `GradingScale`. You are not running two systems — one schema serves both
  cohorts, and a `GradingScale` row can be curriculum-specific
  (CBC "E.E./M.E./A.E./B.E." vs 8‑4‑4 "A–E with points") or even
  subject-specific.
- **Ranking is a re-runnable computation**, not something entered by hand.
  `POST /api/v1/rank/` recalculates `TermPositionRanking` from
  `ExamResult` rows any time marks change, using each `ExamType.weight` —
  so "Opening + Midterm" at the midterm checkpoint and "Opening + Midterm +
  Endterm" at the endterm checkpoint are just two different weighted
  combinations of the same underlying marks.
- **Papers (PP1/PP2) are opt-in per subject** (`Subject.has_papers`), so a
  subject like English can have two or three papers while a subject like
  Physical Education has none — same model, works for both curricula.
- **RBAC is enforced at three levels**: route-level (`permission_classes`),
  row-level (`get_queryset()` filters students/parents to their own data),
  and object-level (`IsAllocatedTeacherForClassroom` for mark entry).

## 5. What's intentionally left for you to extend

- Migrations aren't included (run `makemigrations` after any schema tweak).
- No SMS/M-Pesa STK push integration — `Payment.method` already has an
  `MPESA` choice, ready for Daraja API integration in `services.py`.
- No report-card PDF generation yet — `ExamResult` + `TermPositionRanking`
  have everything a PDF template needs.
- The non-Dashboard/Students frontend pages are scaffolded stubs with the
  exact API calls named in a comment — wire them up following the pattern
  in `pages/admin/Students.jsx`.
